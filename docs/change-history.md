# 変更履歴（決定事項と却下案）

## 2026-11-04 Haas-ja バックエンドの追加

### 背景

Third Intelligence 社が日本語音声認識モデル Haas-ja-v1.0 を公開した。RTX 5060 Ti で
large-v3-turbo と比較した（JSUT・FLEURS 各 200 件、1 発話ずつ推論）。

| モデル | データ | CER strict | CER kana | レイテンシ p50 |
|---|---|---|---|---|
| Haas-ja | JSUT | 4.38% | 0.49% | 28ms |
| large-v3-turbo | JSUT | 6.40% | 0.69% | 182ms |
| Haas-ja | FLEURS | 3.97% | 2.47% | 37ms |
| large-v3-turbo | FLEURS | 4.62% | 2.84% | 239ms |

VRAM のピークは約 3.6GB。読み上げ音声のみの評価で、フィラーや話し言葉は未評価。

### 決定事項

- `STT_BACKEND=whisper|haas` でバックエンドを切り替える。faster-whisper は残す。
- デフォルトは `whisper` とし、稼働中のサービスの動作を変えない。
- Haas-ja の依存（NeMo、torch）は extras `haas` に分ける。venv が約 8GB になるため。
- API の入出力の形は変えず、`/health` と `/transcribe` の応答に `backend` を追加する。
- 認証の環境変数は既存の `STT_API_KEY` のまま変えない。
- haas で `ja` 以外の言語が指定されたら `400` を返す。
- 音声のデコードは PyAV を直接呼ぶ。faster-whisper の `decode_audio` は内部で `gc.collect()` を
  呼び、NeMo を読み込んだプロセスでは 1 回 230ms ほどかかった（推論は約 30ms）。直接呼ぶと
  5〜8ms で、波形の差は最大 1.5e-5。

### 動作確認（テスト用サーバ、RTX 5060 Ti）

| バックエンド | 音声 | レイテンシ（2 回目以降） |
|---|---|---|
| haas | JSUT 4.9 秒（WAV / Opus / WebM） | 40〜47ms |
| haas | JSUT 10 発話を連結した 44 秒（WAV） | 106〜160ms |
| whisper | JSUT 4.9 秒（WAV / WebM） | 約 250ms |

初回のリクエストはモデルの読み込みを含み、haas で約 10 秒かかる。

### 却下した案

- **Whisper を Haas-ja で置き換える**：Haas-ja は日本語専用かつ NVIDIA GPU 専用で、
  多言語や CPU の環境で使えなくなるため。
- **haas-asr の `load_audio` を使う**：WebM を読めず、対応フォーマットが whisper と食い違うため。
  PyAV で直接デコードする。

## 2026-11-13 並列処理とワーカーの定期的な入れ替え

### 背景

利用者が増え、同時に来たリクエストを並列に処理する必要が出た。`/transcribe` が `async def` の
中で推論を直接呼んでいたため、推論中はイベントループ全体が止まり、`/health` も応答しなかった。

### 決定事項

- 推論とモデルの読み込みは別スレッドで実行し、イベントループを止めない。
- 並列化は uvicorn のワーカープロセスを増やして行う（`STT_WORKERS`）。whisper と haas の
  両方に同じ方法で効き、プロセス間で共有する状態が無いため。
- ワーカー内の推論は 1 件ずつに制限する。haas（NeMo）は推論のたびにモデルの状態を書き換え、
  CUDA Graph の固定バッファも共有するため、同じモデルを複数スレッドから同時に呼べない。
- 混雑時はリクエストを拒否せず、待たせる（`503` は返さない）。
- モデルは最初のリクエストではなく、ワーカーの起動時に読み込む。ワーカーの入れ替えのたびに、
  直後のリクエストが読み込みを待たないようにするため。
- `STT_MAX_REQUESTS` で、指定件数を処理したワーカーを入れ替えられるようにする。メモリが
  肥大化しても元に戻すため。既定は無効（`0`）とし、負荷試験でメモリの推移を測ってから値を決める。
- systemd の `Restart` を `always` にする。ワーカーが 1 つのとき、件数の上限で正常終了した
  プロセスを起動し直すため。

### 却下した案

- **1 つのモデルを複数スレッドから同時に呼ぶ**：whisper は faster-whisper の `num_workers` で
  可能だが、haas は上記の理由で安全でない。GPU 上の計算はもともと順番に実行されるため、
  効果も CPU 側の処理と重なる分に限られる。
- **複数リクエストをまとめて推論する（動的バッチング）**：haas では GPU の効率が最も良いが、
  実装が複雑で、混み具合によって結果がまれに変わりうる（haas-asr はバッチサイズで拮抗した
  トークンが変わりうるとしている）。プロセス並列で足りなければ検討する。
- **ジョブキュー化（投入して後で結果を取りに来る形）**：API が変わり、クライアントの改修が必要なため。
- **gunicorn の `--max-requests`**：uvicorn 0.30 以降の `--limit-max-requests` と
  `--workers` で同じことができ、依存を増やさずに済むため。


## 2026-11-15 ストリーミングでの相槌・一時的な返事（/stream）

### 背景

音声対話のクライアントから、話している最中の相槌と、本回答までの沈黙を埋める一時的な返事が
欲しいという要望が出た。`/transcribe` は多くのクライアントが使っているため変えられない。

このホスト（RTX 5060 Ti 16GB、稼働中のほかのプロセスで約 8GB 使用）で次を測った。

- 相槌の予測（MaAI、CPU、VOICEVOX で作った約 18 秒の日本語の語り）

  | モード | 推論の遅れ 中央値 / 95% 値 | CPU | 結果 |
  |---|---|---|---|
  | `bc`（`vap_bc_jp`） | 57ms / 96ms | 約 1.4 コア | 7 回発火し、7 回とも話の間の始まりから 0.05〜0.15 秒以内。最後の質問の後には出なかった |
  | `bc_2type` | 43ms / 80ms | 約 1.2 コア | `bc` とほぼ同じ位置。感情を込めた相槌は一度も出なかった |
  | `vap`（話者交代） | 21ms / 41ms | 約 0.7 コア | 最後の質問の後でも、交代の合図とはっきり読める値にならなかった |

- 一時的な返事（Ollama、8 発話×2 回、「聞き手として相槌を打つ」プロンプト）

  | モデル | 全体の時間 中央値 | GPU メモリ | 結果 |
  |---|---|---|---|
  | gemma4:e2b | 約 340ms | 1.7GB | 2 回とも安定し、話題を拾い、事実の言い切りは無かった |
  | LFM2.5-1.2B-JP | 約 80ms | — | 言い切りは無いが、ほぼ「調べるね」だけで話題を拾わない |
  | Qwen3.5-0.8B | 約 230ms | 560MB | 「東京は晴れだね。」と言い切る。オウム返しもあった |

- 文字起こし（稼働中の Haas、暖まった状態）：6 秒の音声で約 40ms、18 秒で約 55〜80ms。

### 決定事項

- WebSocket の `/stream` を新しく追加し、`/transcribe` と `/health` は変えない。
- 相槌のタイミングは MaAI の `vap_bc_jp` で予測し、文言は固定の候補から順に選ぶ。
  CPU だけで動き、GPU を Haas と取り合わないため。
- 発話の開始と終了はクライアントが通知する。ゲートウェイは無音から発話の終わりを判定しない。
  クライアントが読み上げている間に相槌が出ることも、これで防ぐ。
- 音声は Opus の生パケット（1 メッセージに 1 パケット）を既定にし、16kHz の PCM も受け付ける。
  車載のクライアントから送られるため。約 18 秒の音声で、24kbps の Opus は 52KiB、16kHz の PCM は
  566KiB（約 11 倍）だった。PyAV でのデコードは 1 パケットあたり中央値 0.03ms。
- 一時的な返事は Ollama の軽量 LLM で作り、既定のモデルは gemma4:e2b とする。モデルは設定で変えられる。
- プロンプトは「アシスタント」ではなく「答えを知らない聞き手として相槌を打つ」設定にする。
  アシスタントとして「答えない」と指示した版では、LFM2.5-1.2B-JP と Qwen3.5-0.8B が
  「約 15% 増です」「明日は晴れだね」と事実でない内容を言い切った。
- LLM が時間内に返さない・失敗した・長すぎる場合は、固定の文言を返す。
- `transcript` を `ack` より先に送る。一時的な返事は文字起こしの結果から作るため。
  返事を先にしたい場合の調整は、実際に使ってから検討する。
- 同時に相槌を予測する発話の数をワーカーごとに制限する。上限を超えた発話は切断せず、相槌なしで
  受け付ける（`transcript` と `ack` は送る）。相槌の予測は 1 発話あたり CPU を約 1.4 コア使い続け、
  増やしすぎると全員の相槌が遅れるため。CPU を大きく使うのは相槌の予測だけで、文字起こしと
  一時的な返事は上限と関係なく返せる。
- 予測器は接続ごとではなく発話ごとに貸し出す。車載のクライアントは接続したままになりやすく、
  話していない間に枠を握り続けないようにするため。

### 却下した案

- **Haru-4B（全二重の音声対話モデル）で相槌を作る**：GPU メモリが約 12GB 必要で、
  稼働中の Haas と同じ GPU に載らない。事前学習だけのベースモデルで、決まった返事を
  言わせる制御もできない。利用者の発話の文字起こしもしない。
- **J-Moshi・PersonaPlex・Nemotron VoiceChat**：GPU が大きく必要か、日本語に対応していない。
- **MaAI の `vap_jp`（話者交代）や `vad_jp`（発話区間）で発話の終わりを判定する**：
  非商用ライセンス（CC BY-NC-ND 4.0）のため。発話の終わりはクライアントの通知で足りる。
- **MaAI の `bc_2type`（相槌の種類も予測）**：Hugging Face にライセンスの記載が無いため。
- **LLM に話題と発話の種類だけを JSON で抜き出させ、返事はテンプレートで作る**：
  言い切りは防げるが、「聞き手」のプロンプトの gemma4:e2b のほうが自然で、速かった
  （抜き出しは約 430ms）。
- **相槌の文言も LLM で作る**：日本語の相槌は話の間から 0.2〜0.3 秒で打たれることが多く、
  LLM の生成時間では間に合わない。
- **Opus を Ogg / WebM のコンテナに入れて送る**：サーバ側でコンテナを順に解釈する必要があり、
  ブラウザの MediaRecorder は数百 ms ごとにまとめて出すため相槌が遅れる。車載のクライアントは
  生パケットを送れる。
- **同時接続の上限を超えた接続を切断する**：クライアントごとに `/transcribe` などへの
  フォールバックを作る必要がある。相槌を止めるだけで、残りの機能は提供できる。
- **トークンを URL のクエリで受け取る**：アクセスログやプロキシのログに残るため。

## 2026-11-15 一時的な返事と相槌をクライアントから指定できるようにする

### 背景

ARGOS（この後にエージェントの本回答が続く音声アシスタント）で `/stream` を試したところ、
一時的な返事が本回答と同じ受け止めを繰り返し、違和感があった。

| 発話 | 一時的な返事 | エージェントの本回答 |
|---|---|---|
| 「…全然相槌とか出ねえな」 | 「アルゴスね、どうだった？」 | 「『確認するね』みたいな相槌が出なくなったんだね。…」 |
| 「…ちょっと違和感がやっぱりある気がするよね」 | 「違和感あるんだね。」 | 「なるほど、新しい相槌は出るけど、しっくりこないんだね。…」 |

既定のプロンプトは「相手の言葉を少し繰り返してよい」としており、一時的な返事で受け止めて
終わるクライアントには合うが、本回答が後に続くクライアントには合わない。聞き返し
（「どうだった？」）の後に別の本回答が始まるのも不自然だった。合う言い方はクライアントの
作りで決まるため、サーバの設定 1 つでは決められない。

### 決定事項

- `start` に `ack`（`system_prompt`・`examples`・`fallback_text`・`max_chars`、または `false`）と
  `backchannel`（`phrases`・`threshold`・`min_interval_ms`）を追加し、発話ごとに指定できるようにする。
  省略した項目はサーバの設定を使い、既存のクライアントの動作は変えない。
- `system_prompt` を指定して `examples` を省略したときは、既定の会話例を使わない。既定の会話例は
  既定のプロンプトの言い方に合わせてあり、別の指示と混ぜると食い違うため。
- 指定できる長さと個数に上限を設ける。範囲外や未知のフィールドは `invalid_message` にする。
- モデル・推論の設定・出力の整形と差し替えの規則、予測器の上限は、クライアントから変えられない。
- 本回答が後に続くクライアント向けのプロンプトを `gemma4:e2b` で試した（ARGOS で実際に話した発話
  3 件とよくある依頼 3 件、各 2 回）。

  | プロンプト | 結果 |
  |---|---|
  | 既定（聞き手・繰り返してよい） | 「違和感あるんだね。」「ずれがあるんだね。」と繰り返す |
  | 「音声アシスタントのつなぎ役」として内容に触れない | 6 件中 3 件が韓国語。「明日の天気は晴れだよ。」と言い切る |
  | 「聞き手」のまま、繰り返し・聞き返しを禁じ、日本語を指定 | 「そうなんだ、見てみるね。」「ちょっと見てみるね。」。繰り返し・言い切り・他言語なし。約 330ms |

  3 つ目を README の例にする。「アシスタント」として書くと答えてしまうことは、クライアントが
  プロンプトを書く場合にも当てはまる。

### 却下した案

- **接続の最初に 1 回だけ設定を送る**：ARGOS のように発話ごとに接続し直すクライアントでは毎回
  送ることになり、`start` に含めるのと変わらない。状態を持つ分だけサーバが複雑になる。
- **サーバ側に名前付きのプロンプトを用意し、クライアントは名前を送る**：プロンプトを直すたびに
  サーバの設定の変更と再起動が要り、クライアントの試行錯誤が遅くなる。
- **直前の会話（前の発話や本回答）を渡せるようにする**：中身のない「つなぎ」の一言には文脈が
  要らない。プロンプトの指定で足りるか ARGOS で確かめてから判断する。

## 2026-11-15 相槌の文言を話の種類に合わせて選ぶ（Kev）

### 背景

ARGOS で、相槌の文言を順に回すだけでは中身と合わない（困っている話に「まじか」など）ため、意味の
ある相槌を使えなかった。タイミングは MaAI のまま、文言だけを話の中身から選ぶ方法を比べた。
途中までの書き起こし 26 件（テスト音声を MaAI の相槌の位置で切った 5 件と手作りの 21 件。正解は
手で付けた）で、候補（うん・そっか・なるほど・そうなんだ・へえ・出さない）を選ばせた。

| 方式 | 合っていた件数 | 時間 |
|---|---|---|
| いつも「うん」 | 9/26 | — |
| gemma4:e2b に候補から選ばせる（16 件で比較） | 7/16 | 約 380ms |
| Kev-0.8B に候補から選ばせる（日本語の指示、「うん」が先頭） | 13/26 | 約 30ms |
| 同上、「うん」を最後に並べる | 15/26 | 約 20ms |
| Kev-0.8B に「話し手が今何をしているか」を日本語の指示で選ばせる | 18/26 | 約 20ms |
| **同上、英語の指示** | **23/26** | **約 20ms** |
| 同上、選択肢の並び順を 4 通り変えて平均 | 24/26 | 約 70ms |

途中の文字起こし（Haas）は 1 回 50〜60ms。合計で、相槌を出すと決めてから約 70ms で文言が決まる。

### 決定事項

- タイミングは MaAI のまま、文言は Kev-0.8B に話の種類（7 種類）を英語で選ばせ、種類ごとの文言を
  クライアントが `start` の `backchannel.phrases_by_kind` で指定する。指定しない発話は今までどおり。
- 判定が `STT_BACKCHANNEL_JUDGE_TIMEOUT_MS`（既定 200ms）に間に合わない、または失敗したら、その
  相槌は出さない。遅れた相槌は話の続きにかぶるため。
- `backchannel` イベントに判定した `kind` を足す（今のクライアントは無視できる）。
- Kev は別のサービスとして `127.0.0.1` で動かし、Bearer トークンを必須にする。
- 並び順の平均は使わない。1 件しか良くならず、時間が 3 倍になるため。

### 却下した案

- **相槌の文を LLM に自由に書かせる**：途中の文字起こし・生成（約 0.3 秒）・クライアントでの合成
  （0.1〜0.3 秒）で、話の間から 0.5〜0.8 秒かかり、話の続きにかぶる。
- **gemma4:e2b に候補から選ばせる**：「そうなんだ」に偏り（7/16）、約 380ms かかる。
- **Kev-4B**：Kev-0.8B と同じ聞き方（候補から選ばせる）では正答が増えなかった。このマシンの GPU の
  空き（約 7GB）にも載らない。ただし「話の途中か」の判定は 0.8B より値がはっきり出た。
- **TypeSafe Jev（クラウドの API）**：話した内容を外部に送ることになり、回線の遅れも加わる。日本語は
  主対象ではない。
- **DuplexJev（音声を直接判定）**：4B 版で GPU 約 10GB が要り載らない。モデルは非商用ライセンス。

## 2026-11-15 後半の相槌が言いよどみとして見送られる問題

- ARGOS 側で分類なし5回・分類あり2回という比較が報告された（Codex、chives、
  2026-11-15 10:12 JST、原文 ID

## 2026-11-15 話の種類を 14 にし、種類ごとに複数の文言を指定できるようにする

### 背景

ARGOS で試したところ、同じ種類で毎回同じ言葉になると機械的に聞こえた。また、話し終わりの相槌の
直後に一時的な返事が重なること、「〜だよね」「〜と思う」に合う相槌が無いことが挙がった。
ARGOS 側の聞き比べで、使う言葉は「うん・そっか・なるほど」になった（「へえ」「そうなんだ」は声に
よって不自然だった）。

種類を 7 つから 14 に増やして、Kev-0.8B で 47 件（前回の 26 件、新しい種類の例 16 件、ARGOS で
実際に話した発話 5 件）を判定し、ARGOS の対応付けで出る相槌が合っているかを比べた。

| 分け方 | 合っていた件数 | 時間（中央値） |
|---|---|---|
| 7 種類 | 37/47 | 28ms |
| 14 種類（`opinion` を「なるほど」に対応） | 40/47 | 30ms |
| 14 種類（`opinion` を「うん」に対応） | 42/47 | 30ms |

増やした種類は、`wrapping_up`（「以上です。」「まあ、そんなところかな。」）、`seeking_agreement`
（「〜だよね？」）、`thinking_aloud`（「どうしようかな、」）をおおむね当てた。外れの多くは
`opinion` の選びすぎで、ARGOS の「〜な気がするな」がここに入る。

### 決定事項

- 種類を 14 にする（`seeking_agreement`・`opinion`・`happy`・`complaint`・`step_by_step`・
  `thinking_aloud`・`wrapping_up` を追加）。分類の精度は落ちず、クライアントが選べる対応付けが増える。
- `phrases_by_kind` の値に、1〜5 個の配列も書けるようにし、種類ごとに順に使う。同じ文言が続くのを
  避けるのは、`phrases` と同じくサーバ側で行い、どのクライアントでも同じように使えるようにする。
- 「ときどき相槌を打たない」はクライアントに任せる。好みがクライアントごとに分かれるため。

### 却下した案

- **`kind` だけを返し、文言の選択と順番はクライアントが持つ**：クライアントごとに同じ仕組みを
  作ることになる。`phrases` と扱いがそろわない。
- **並び順を変えて何度か聞き、平均する**：7 種類のときに 1 件しか良くならず、時間が 3 倍になった。

## 2026-11-15 話の種類の判定を、確率が上がり始めた時点で始める

### 背景

ARGOS で話すと、相槌が話の続きにかぶり、回数も少なかった。ARGOS 側のマイクの取り込み
（80ms ずつ）、予測（100ms ごと）、途中の文字起こしと Kev の判定（ログで 100〜150ms）、
ARGOS での再生（aplay と PipeWire で約 50ms 以上）を合わせると、話が止まってから 300〜450ms 後に
鳴る。話の切れ目は 300〜500ms ほどで終わるため、話し始めた頃に重なる。
実際の音声で測ると、MaAI の確率は話が止まった最初のフレームでしきい値を超えており、
1 フレームの推論は約 7ms だった。ゲートウェイの中で最も長いのは、種類の判定の待ち時間だった。
ARGOS の 30 秒の発話では、相槌を出すと決めたのが 3 回だけだったが、ARGOS のマイクの音で
確率がどこまで上がっているかはログから分からなかった。

### 決定事項

- 確率がしきい値の 2/3 を超えたところで判定を先に始め、同じ山でしきい値を超えたらその結果を使う。
- 発話ごとに確率の山をログに残し、しきい値の調整に使う。

### 却下した案

- **予測器へ渡すチャネルの順番を入れ替える**：`vap_bc` の説明では 1 つ目のチャネルがシステム側と
  されているが、実際の音声で入れ替えると確率がほとんど 0 のままだった。今の順番（ユーザの音声を
  1 つ目、無音を 2 つ目）では話の切れ目で確率が上がる。
- **しきい値に届く前に相槌を送る**：遅れは減るが、しきい値に届かなかった山でも相槌が鳴る。
- **毎フレームの確率をログに出す**：1 発話で数百行になる。しきい値の調整には山だけで足りる。

ARGOS の音では、確率の山が 0.3〜0.55 に固まり、テスト用の音声（切れ目で 0.5〜0.65、話している間は

## 2026-11-15 相槌のタイミングを、Silero VAD で無音が続いたことで決められるようにする

### 背景

ARGOS の録音 4 発話（75 秒、200ms 以上の切れ目 27 個）で、MaAI（しきい値 0.35）は相槌 10 回が
すべて話の途中に出ていた。切れ目でも確率がほとんど上がらず、50〜150ms の息継ぎで上がっていた。
推論を 50ms ごとにしても、切れ目でも話の途中でも確率が上がるだけで、位置は変わらなかった。
無音の長さだけで決めると、切れ目 27 個のうち 18〜19 個に出せた。

### 決定事項

- `backchannel.timing` に `silence` を足し、Silero VAD で話していない状態が `silence_ms` 続いたら
  相槌を出す。出すかどうかの内容の判断（質問・言いよどみ・締めには出さない）は Kev の種類に任せる。
- 既定は `maai` のままにする。今のクライアントの動きを変えないため。
- `silence_ms` の既定は 90ms。録音では 90・120・150ms で切れ目に出せた数（20/27）が同じで、
  遅れだけが 211・243・275ms と増えた。

### 却下した案

- **RMS で無音を判定する**：人工の低域雑音で SNR 10dB にすると誤反応が 4 倍、0dB で 13 倍になった。
  雑音の大きさを順に推定しても、変わる雑音（音楽・人の声）には追いつけない。
- **WebRTC VAD**：雑音なしでは Silero と同程度だが、SNR 0dB で誤反応が 15 回（Silero は 3 回）。
  無音とみなす長さを短くすると誤反応が大きく増えた。
- **MaAI の確率と無音の両方を条件にする**：話の途中には出なくなるが、切れ目に出せた数が 8/27 に減った。
- **MaAI を 50ms ごとに推論する**：上のとおり位置が変わらず、CPU が 2 倍になる。
- **faster-whisper 同梱の Silero VAD モデル**：1 チャンクずつ呼ぶと確率が silero-vad と大きくずれた。

## 2026-11-15 長い話では相槌の間隔を広げ、長い発話でも種類の判定を間に合わせる

### 背景

`silence` で 60 秒話すと、相槌が 56 秒で 17 回（ほぼ `min_interval_ms` の 2.5 秒おき）出て多すぎた。
人は相手の話が長くなるほど相槌を減らす。また、その発話は 60.02 秒で
`STT_STREAM_MAX_UTTERANCE_SECONDS`（60 秒）を超えて捨てられ、以後の相槌も文字起こしも返らなかった。
種類の判定のための途中の文字起こしを発話の頭から行っていたため、50 秒を過ぎると判定に
150〜175ms かかり、待つ上限（200ms）に近づいていた。

### 決定事項

- 最短の間隔を、経過時間（1 分ごとに足す）と相槌の回数（1 回ごとに掛ける）の両方で伸ばし、上限で止める。
  既定は 1 分ごとに 3 秒、1.1 倍、上限 8 秒。既定で伸ばすのは、間隔をどう空けるかは相槌を出すかを
  決めるゲートウェイの役目で、クライアントごとに作らせないため。
- 種類の判定のための途中の文字起こしを、直近 15 秒だけにする。
- 本番の `STT_STREAM_MAX_UTTERANCE_SECONDS` を 180 秒にする（コードの既定は 60 秒のまま）。

### 却下した案

- **経過時間だけ、または回数だけで伸ばす**：経過時間だけだと相槌が続けて出た後も間隔が変わらず、
  回数だけだと相槌が出ないまま長く話した後に急に間隔が広がらない。両方を組み合わせる。
- **直近 8 秒・10 秒**：頭からと同じ種類になった数が 25 か所中 9 か所・15 か所で、判定が変わりすぎた。
