# コンセプト

## 目的

音声ファイルを HTTP で受け取り、文字起こし結果を JSON で返すゲートウェイ。
クライアント（音声入力アプリや AI エージェント）は、音声認識エンジンの違いを意識せずに
同じ API で文字起こしを使える。

あわせて、音声対話のクライアント向けに、音声をストリーミングで受け取りながら
「うん」「なるほど」などの相槌と、「〇〇ね、確認するね」などの一時的な返事を返す API を持つ。
本回答を作るまでの沈黙を埋め、話を聞いていることを利用者に伝えるため。

## 方針

- **エンジンを差し替えられる**：faster-whisper（多言語）と Haas-ja（日本語専用）を設定で切り替える。
  API の入出力は、どちらのエンジンでも同じ形にする。
- **日本語の精度と応答速度を重視する**：主な用途は日本語の音声指示。日本語の評価で
  Whisper を上回るエンジン（Haas-ja）を選べるようにする。
- **重い依存は必要な人だけが入れる**：Haas-ja は NeMo と torch を必要とし、環境が数GB 増える。
  Whisper だけを使う環境には入れない。
- **閉じたネットワークでも最低限の認証を持つ**：Bearer トークンで保護する。
- **既存の API は変えない**：`/transcribe` と `/health` は多くのクライアントが使っているため、
  ストリーミングは別の API（`/stream`）として追加する。
- **相槌と一時的な返事は答えを言わない**：ゲートウェイは質問の答えを知らない。
  相槌は「聞いている」ことだけを、一時的な返事は「受け止めた」ことだけを伝え、
  事実を言い切る内容は返さない。本回答はクライアント側の仕組みが作る。
- **相槌は軽く、一時的な返事は少しだけ賢く**：相槌は話の間に遅れず返す必要があるため、
  CPU で動く専用の予測モデルでタイミングだけを決め、文言は固定の候補から選ぶ。
  一時的な返事は発話の終わりに一度だけ返すため、軽量 LLM で話題を拾った一言にする。
- **発話の区切りはクライアントが決める**：発話の開始と終了はクライアントが通知する。
  `/transcribe` と同じく「1 発話を 1 単位として扱う」区切り方をそろえるため。
